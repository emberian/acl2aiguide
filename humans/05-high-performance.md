# 5. High-performance software in ACL2

ACL2 functions run. The same `defun` that the prover reasons about is
compiled by the host Common Lisp and executed, and a function whose guards
are verified has its guard checked once, at entry, and then runs as plain
compiled Lisp: "the guard is checked upon the top-level entry to your system
and then raw Common Lisp does all the computing" [:doc
guards-and-evaluation]. That is the whole opportunity and most of the
danger: what runs is not always the text
you proved things about, the logic happily describes representations that
cost sixteen bytes per element, and nothing in a green certificate says how
much a served operation allocates.

This chapter is about writing ACL2 that is fast as executed code: which
body runs when, how to allocate once and never again, how to find the
consing, how to batch, how to structure the program as one loop, how
TigerBeetle's rules translate, how code generation gets a small shipped
core, and what a layer of generating macros buys and costs. fn, the
ACL2-verified NNTP server, is the worked example throughout, including
where it went wrong.

## 5.1 What runs when: the executable/logical split

### What goes wrong

- **The `:logic` side of an `mbe` runs, not the `:exec` side.** A function
  whose guards are not verified is evaluated through its executable
  counterpart, and there an `mbe` evaluates its `:logic` code. Measured on
  one function with an `mbe` whose `:logic` builds a filtered list and whose
  `:exec` counts in a loop, called on a 100,000-element list: the
  guard-verified copy allocated 0 bytes; the identical copy declared
  `:verify-guards nil`, reached through `ec-call`, allocated 851,760 bytes,
  the list its `:logic` built [example: examples/performance/what-runs.lisp]
  [measured: `examples/certify.sh performance/what-runs.lisp`, its
  `.cert.out`; laptop].
- **A guard you did not mean to run, runs on every call.** fn's rule for its
  served path: "A native dispatch `(fnn-core 'f ...)` calls f's executable
  counterpart, so **f's guard is evaluated on every call**. A whole-state
  recognizer in the guard of a function the host calls is therefore a walk
  per request" [fn: docs/proof-style.md:873-876 @3bbfc4dca]. fn measured the
  cost of exactly that: its state recognizer `fn-statep` "is Theta(n^2) in
  Message-ID comparisons and Theta(n*P) in octet checks, and it ran on every
  served operation and four times per replayed record" [fn:
  docs/proof-style.md:301-303 @3bbfc4dca].
- **An unverified recursion runs as a recursion.** fn's record log found
  that "an unverified function's *1* ran its recursion, one control-stack
  frame per record or octet" when the host reached it through a fallback
  path; the cure was to verify the guards of every function on the path
  [fn: books/store-log.lisp:102-108 @3bbfc4dca].
- **The `:logic` of an `mbe` is still stobj code.** Writing the list view of
  a stobj as the `:logic` of an `mbe` is refused at translation: "A
  single-threaded object, namely TAGTAB, is being used where an ordinary
  object is expected" [example: examples/performance/mbe-fixnum-loop.lisp].
  The list view lives in a theorem instead (5.2).

### The mechanism

Every ACL2 function is two Common Lisp functions. The manual: "every ACL2
function symbol is associated with the following two Common Lisp
definitions ... the ``executable-counterpart'' definition, sometimes called
the ``*1*'' function ... and the ``submitted'' definition (sometimes called
the ``raw Lisp'' function)" [:doc evaluation]. The executable counterpart
"is generated by ACL2 to include not only code to check guards, but also code
to invoke the executable-counterparts of its callees" [:doc evaluation]. When
the guards of a function are verified, its executable counterpart checks the
guard once and "escapes to the submitted definition if the guard holds of the
arguments and the function has already had its guards verified. Otherwise
the executable-counterpart evaluates the body of the function by calling the
executable-counterpart of each subroutine" [:doc guards-and-evaluation].

The `mbe` macro is the switch between the two bodies. Quoting the obligation
whole: "In the ACL2 logic, `(mbe :exec exec-code :logic logic-code)` equals
`logic-code`; the value of `exec-code` is ignored. However, in raw Lisp it is
the other way around: this form macroexpands simply to `exec-code`. ACL2's
guard verification mechanism ensures that the raw Lisp code is only evaluated
when appropriate, since the guard proof obligations generated for (the
macroexpansion of) this call of `mbe` include not only the guard proof
obligations from `exec-code`, but also, under suitable contextual
assumptions, the term `(equal exec-code logic-code)`" [:doc mbe]. And which
side runs: "Normally, during evaluation of an `mbe` call, only the `:logic`
code is evaluated unless the call is in the body of a guard-verified
function or under a call of a `:program` mode function; in those cases only
the `:exec` code is evaluated. This implies that equality of `:exec` and
`:logic` code is never checked at runtime" [:doc mbe]. The two exceptions
the same paragraph names matter for test books: in "safe mode", "used in
macroexpansion and evaluation of `defconst` forms, the `:logic` and `:exec`
code are both evaluated and their equality is checked", and under guard
checking `:all` or `:none` only `:logic` runs in a `:logic`-mode body [:doc
mbe].

`:program` mode is the third case. "In general we treat `:program`
functions much as we treat `:logic` functions whose guards have been
verified, except that when no error occurs then the corresponding raw Lisp
function is always called" [:doc guards-and-evaluation]. So "when a guard has
been satisfied on a call of a function with `:program` mode, no subsidiary
guard checking will be done" [:doc guards-and-evaluation], which is fn's
rule that "anything below a `:program` host wrapper run[s] raw Lisp. There
`mbe` runs `:exec` and no callee guard is evaluated" [fn:
docs/proof-style.md:871-872 @3bbfc4dca].

The four cases, measured with the same `count-evens` pair (one verified,
one `:verify-guards nil`) on a 100,000-element list, bytes allocated by the
call alone [example: examples/performance/what-runs.lisp] [measured:
`examples/certify.sh performance/what-runs.lisp`, `.cert.out` lines
234-239; laptop]:

| caller | callee | body that ran | bytes |
| --- | --- | --- | ---: |
| guard-verified | guard-verified | raw, `:exec` | 0 |
| guard-verified, through `ec-call` | unverified | `*1*`, `:logic` | 851,760 |
| `:program` mode | unverified | raw, `:exec` | 0 |
| unverified (`*1*`) | guard-verified | callee's `*1*` checks its guard, then raw `:exec` | 0 |

The last row is why a verified callee is cheap even under an unverified
caller: the guard check happens once, at the boundary, and then raw code
runs. It is also why the guard itself is the cost when it is a whole-state
recognizer.

How fast guard-verified code is, by itself, is smaller than people expect.
The manual's own estimate: "We believe that in most cases, the
executable-counterpart executes almost as fast as the submitted definition,
at least if the evaluation of the guards is fast. So, the main advantage of
guard verification is probably that it lets you know that the submitted
function may be executed safely in raw lisp, returning the value predicted by
the ACL2 logic, whenever its arguments satisfy its guard" [:doc
guards-and-evaluation]. The large effects come from the two things guard
verification switches on: the `:exec` side of every `mbe`, and the type
declarations the host compiler may trust (next section). The manual adds
that "guard verification might be important for optimal efficiency when the
functions make use of type declarations" [:doc guards-and-evaluation].

`mbt` is the one-sided form, and it is not a runtime assertion. "Semantically,
`(mbt x)` equals `x`. However, in raw Lisp `(mbt x)` ignores `x` entirely,
and macroexpands to `t`. ACL2's guard verification mechanism ensures that the
raw Lisp code is only evaluated when appropriate, since a guard proof
obligation `(equal x t)` is generated" [:doc mbt]. It exists so that a test
needed for termination or for the logic costs nothing in execution: "since
`(mbt <g>)` expands to `t` in raw Lisp, then once we verify the guards of
`foo`, the evaluations of `<g>` will be avoided (except at the top level,
when we check the guard before allowing evaluation to take place in Common
Lisp)" [:doc mbt]. fn writes the same thing as `(mbe :logic (not (fn-statep
s)) :exec nil)` at the top of a transition, so that "non-states are still
returned unchanged in the logic; the `:exec` path relies on the guard" [fn:
docs/proof-style.md:271-282 @3bbfc4dca].

### The shape to copy

A guard-verified wrapper whose `mbe` puts a proof-friendly recursion on the
`:logic` side and a constant-stack loop on the `:exec` side, the equality
proved once as the bridge, and the list view of a stobj stated as a theorem
about the wrapper:

```lisp
(defun count-tag-st (x tagtab)
  (declare (xargs :stobjs tagtab
                  :guard (unsigned-byte-p 61 x)))
  (mbe :logic (count-tag-rec x 0 tagtab)
       :exec (count-tag-loop x 0 0 tagtab)))

(defthm count-tag-st-is-count-tag
  (implies (tagtabp tagtab)
           (equal (count-tag-st x tagtab)
                  (count-tag x (nth *tagi* tagtab)))))
```

[example: examples/performance/mbe-fixnum-loop.lisp]. The book ends by
asserting that the wrapper and its loop are `:common-lisp-compliant`
(guard-verified), because that is the property the execution depends on and
it is cheap to check:

```lisp
(assert-event (eq (symbol-class 'count-tag-st (w state)) :common-lisp-compliant))
```

fn turned this into an entry rule: its `definterface` form for a
host-called entry declares the entry's class (":common-lisp-compliant
(guard-verified), :ideal or :program -- ACL2's symbol-class") and is
"checked against the WORLD when it is admitted", so "a declaration of
:common-lisp-compliant is a claim that the entry is guard-verified, and the
world confirms it" [fn: books/definterface.lisp:13-41 @3bbfc4dca]. Its
`:raw-with` option records "RAW DISPATCH (D40): the host calls the
guard-verified definition, not its executable counterpart", with the named
theorems that carry the guard conjuncts the entry does not evaluate [fn:
books/definterface.lisp:29-34 @3bbfc4dca].

## 5.2 Static allocation: fixed-size stobjs

### What goes wrong

- **Growing an array one slot at a time is quadratic.** fn's first linear-
  hashing Message-ID table "resized a page-pointer array by one per split,
  O(P) a split and O(P^2) in all"; measured over 3.67M adds to 8,193 pages,
  the worst add allocated 114,752 bytes and the mean 168 bytes, against
  49,408 and 96 after the table was rebuilt as a two-level directory that
  grows by one page per split [fn: books/msgid-linear-exec.lisp:7-24
  @3bbfc4dca]. The manual's warning is one sentence: "Array resizing is
  relatively slow, so we recommend using it somewhat sparingly" [:doc
  defstobj].
- **`:resizable nil` does not stop a call to the resizer.** For a field
  declared `:resizable nil`, ACL2 still defines `resize-keys`; it is
  guard-verified with guard `(tblp tbl)`, logically the identity on the
  stobj, and a hard error when executed ("The array field corresponding to
  accessor KEYSI of stobj TBL was not declared :resizable t. Therefore, it is
  illegal to resize this array") [example:
  examples/performance/bounded-table.lisp]. A guard-verified caller of it
  certifies and fails when it runs; the example proves
  `tbl-grow-is-the-identity-in-the-logic` and then shows the call failing
  under `must-fail` [example: examples/performance/bounded-table.lisp].
  The manual: the resize function "modifies the length of the field if
  `:resizable t` was supplied with the field when the `defstobj` was
  introduced and otherwise causes an error" [:doc defstobj].
- **`with-local-stobj` allocates its stobj on every call.** Its expansion is
  `(let ((st (create-st))) ...)` [:doc with-local-stobj], so a scratch stobj
  made per call is a fresh array per call. Measured: 1,000 calls of a
  function that takes a 2,048-word scratch stobj with `with-local-stobj`
  allocated 16,384,928 bytes (16 KiB per call); 1,000 steps over one
  `with-local-stobj` threaded through the loop allocated 51,152 bytes in all
  [example: examples/performance/time-list-vs-stobj.lisp] [measured:
  `examples/certify.sh performance/time-list-vs-stobj.lisp`, `.cert.out`
  lines 801-802; laptop]. `profile` and `memsum` give the same figure per
  call: "Heap bytes allocated per call 1.64e+4" for the per-call function
  [measured: `(include-book ".../time-list-vs-stobj")`, `(profile
  'scratch-per-call)`, `(scratch-per-call-k 1000 0)`, `(memsum)` in the
  laptop REPL].
- **A large stobj can cost the prover what it costs the machine.** The
  creator of a stobj is logically a list as long as its arrays, and a guard
  conjecture about a stobj made by `with-local-stobj` mentions the creator.
  A first draft of the timing example defined, over a 1,000,000-word local
  stobj,

  ```lisp
  (defun bench-stobj ()
    (declare (xargs :guard t))
    (with-local-stobj vec
      (mv-let (r vec)
        (let ((vec (time$ (vec-fill 0 vec) :msg "stobj fill: ~sa bytes, ~st s~%")))
          (mv (vi 5 vec) vec))
        r)))
  ```

  and its guard conjecture was `(LET* ((VEC (CREATE-VEC)) (VEC (VEC-FILL 0
  VEC))) (< 5 (V-LENGTH VEC)))`, a term with no variables. Under `timeout
  120` the event ended `Time: 119.49 seconds (prove: 0.00, print: 0.00,
  other: 119.49)`, "No checkpoints to print", FAILED; that was the timeout's
  signal aborting the event, not ACL2 giving up, and the same form under
  `timeout 240` was still running when it was killed [measured: the form
  above after `(defconst *n* 1000000)`, the `vec` defstobj and `vec-fill` of
  `examples/performance/time-list-vs-stobj.lisp`, piped into the laptop
  REPL, once under `timeout 120` and once under `timeout 240`]. The `prove:
  0.00` is fn's signature for work that is not proof search [fn:
  docs/proof-style.md:591-605 @3bbfc4dca]. The certified book proves
  `(vecp (create-vec))` and disables `create-vec` right after the
  `defstobj`, and the book's own `bench-stobj` admits in 0.01 s [example:
  examples/performance/time-list-vs-stobj.lisp].

### The mechanism

A stobj array field is declared with a fixed length and an initial value,
and is resizable only on request. From the manual's general form:
`(fieldi :type typei :element-type etypei :initially vali :resizable bi)`;
for an array type `(ARRAY type-spec (max))`, "the field is supposed to be a
list of items, initially of length specified by `max`, each of which
satisfies the indicated `type-spec`. `Max` must be a non-negative integer or
a defined constant evaluating to a non-negative integer", and "the initial
value of the field is a list of `max` repetitions of `vali`" [:doc
defstobj]. The object is "modified in place, rather than copied, where for
an array or hash-table field the update is made to a corresponding raw Lisp
array" [:doc defstobj].

Three options of `defstobj` are performance options.

- `:inline t`: "the generated access and update functions for the stobj
  should be implemented as macros under the hood (which has the effect of
  inlining the function calls)" [:doc defstobj]. The manual's numbers:
  "there have been contrived examples, doing essentially nothing except
  accessing and updating array fields, where inlining reduced the time by a
  factor of 10 or more; and inlining has sped up realistic examples by a
  factor of at least 2"; the cost is that "redefinition may not work as
  expected" and that tracing "will not show their calls" [:doc defstobj].
- `:element-type t` changes the raw array's declared element type. The
  manual reports it measured on a `double-float` array of 10^8 elements:
  with SBCL, 100,000,000 reads took 0.23 s with it and 0.21 s without, and
  writes 0.24 s and 0.25 s, on a 2019 MacBook Pro
  [:doc defstobj-element-type]. It is a CCL option more than an SBCL one.
- `:non-executable t` "avoids actually creating a global stobj", for a
  stobj used only through `with-local-stobj` or as the type of another
  stobj's field [:doc defstobj]. The timing example declares both of its
  stobjs this way, so including the book allocates neither [example:
  examples/performance/time-list-vs-stobj.lisp].

The word type is what makes a scan allocation-free. fn's page words are
`(unsigned-byte 61)`: "Every word is a fixnum on SBCL x86-64, so the accessor
returns it unboxed and the scan allocates nothing. MEASURED on the flat
predecessor of this representation (persvati, 2026-10-01,
sb-ext:get-bytes-consed around 10,000 lookups on tables of 10,000 entries):
fn-mpxt-candidates 6,364 bytes consed per lookup, fn-mlh-candidates 16 (the
one cons of the result list)" [fn: books/msgid-linear-exec.lisp:26-36
@3bbfc4dca]. On the laptop (arm64, not x86-64) a 1,000,000-word array of
`(unsigned-byte 61)` cost 8,000,016 bytes to create, eight bytes a word, and
filling it and scanning it a hundred times allocated nothing [example:
examples/performance/time-list-vs-stobj.lisp] [measured: `time-list-vs-stobj.cert.out` lines
792-795; laptop].

The declarations that tell the compiler so are `type` and `the`, and both
are guard obligations. "A call of `(the TYPE EXPR)` in the body of a
function definition generates a guard proof obligation that the type,
`TYPE`, holds for the value of the expression, `EXPR`", and "For `THE` to
provide any execution speed benefit, guards must be verified"; where guards
are not verified, "`THE` acts as a low-level, run-time type check" [:doc
the]. A `type` declaration on a formal is, by default, part of the guard;
`:split-types t` instead makes guard verification "require that these terms
are proved under the hypothesis that the guard holds" [:doc note-6-2]
[:doc guards-and-evaluation]. The manual's own advice on numbers: "consider
using type declarations for numbers in place of `xargs` `:guard`" [:doc
efficiency].

Common Lisp's other performance declarations are not available: "There are
also other kinds of Common Lisp declarations that ACL2 does not support,
e.g., pertaining to inlining, safety settings, variable lifetime, and so
forth" [:doc declare]. There is no `(declare (optimize ...))` in an ACL2
definition. Inlining is asked for by event instead: `defun-inline` defines
`f$inline` and a macro `f` whose calls expand to it, "in order to encourage
the host Lisp compiler to inline calls of `f`" [:doc defun-inline]. fn's
page reader is one, with the macro name registered for theory expressions:
`(defun-inline fn-mlh-word (p i fn-mlh) ...)` followed by `(add-macro-fn
fn-mlh-word fn-mlh-word$inline)` [fn: books/msgid-linear-exec.lisp:244-263
@3bbfc4dca].

Two things the guard proof of such a loop needs, both visible in the
example. Either one missing is enough to refuse the loop, and the book keeps
both drafts as `local` `must-fail` records (`count-tag-loop-draft-1` and
`-draft-2`) [example: examples/performance/mbe-fixnum-loop.lisp]; the goal
texts quoted below are from the drafts' REPL output [measured: the drafts
outside `must-fail`, laptop REPL].

1. The element facts, stated over the field's recognizer. Once the stobj's
   recognizer opens, a goal about `(tagi i tagtab)` reads `(nth i (car
   tagtab))`. The draft had one rewrite rule concluding `(unsigned-byte-p 61
   (nth i l))`, and the goals `(ACL2-NUMBERP (NTH I (CAR TAGTAB)))` and
   `(<= 0 (NTH I (CAR TAGTAB)))` stayed open; the example proves
   `tagp-nth-natp` as a `:type-prescription` rule and `tagp-nth-below` as a
   `:linear` rule instead. fn writes an element lemma and an update lemma for
   each page stobj, locally (`fn-mlg-wp-nth-word`, `fn-mlg-wp-of-update-nth`)
   [fn: books/msgid-linear-exec.lisp:146-153 @3bbfc4dca]; the bounded-table
   example needs the update lemma too (`keysp-of-update-nth`) [example:
   examples/performance/bounded-table.lisp].
2. The arithmetic conjuncts that make the declarations true, first. The
   draft's `:guard (and (<= i *slots*) (<= acc i))` with `(type (integer 0
   1024) i)` left the goal `(RATIONALP I)`: the guard of the `:guard`'s own
   `<=` was not discharged by the type declaration. The certified form leads
   its `:guard` with `(natp i) (natp acc)`.

### The shape to copy

The loop from the example, whole: a fixed array, every formal declared, the
termination test as an `mbe` so raw code compares two fixnums, every sum
wrapped in `the`:

```lisp
(defconst *slots* 1024)

(defstobj tagtab
  (tag :type (array (unsigned-byte 61) (*slots*)) :initially 0 :resizable nil)
  :inline t)

(defun count-tag-loop (x i acc tagtab)
  (declare (xargs :stobjs tagtab
                  :guard (and (natp i) (natp acc) (<= i *slots*) (<= acc i))
                  :measure (nfix (- *slots* (nfix i))))
           (type (unsigned-byte 61) x acc)
           (type (integer 0 1024) i))
  (if (mbe :logic (or (not (natp i)) (>= i *slots*)) :exec (= i *slots*))
      acc
    (count-tag-loop x
                    (the (integer 0 1024) (+ 1 i))
                    (if (= x (the (unsigned-byte 61) (tagi i tagtab)))
                        (the (unsigned-byte 61) (+ 1 acc))
                      acc)
                    tagtab)))
```

[example: examples/performance/mbe-fixnum-loop.lisp]. And a fixed table
whose insert refuses by name when full and returns the stobj unchanged,
which is a theorem:

```lisp
(defthm tbl-insert-full-is-a-refusal-and-a-no-op
  (implies (and (tblp tbl)
                (<= *table-cap* (used tbl)))
           (and (equal (mv-nth 0 (tbl-insert k tbl)) :full)
                (equal (mv-nth 1 (tbl-insert k tbl)) tbl))))
```

[example: examples/performance/bounded-table.lisp]. Scratch space that a
loop needs belongs in one stobj threaded through the loop, or in a field of
the long-lived stobj; `with-local-stobj` is for a computation that runs once
per request at most, and its return shape is fixed: the `mv-let` binds the
stobj and the body returns the other values only [:doc with-local-stobj].
fn's lane that wrote differential tests over stobjs recorded the same rule
after paying for it: "the body returns the other values and NOT the local
stobj ... A stobj argument must be a variable, never a call: bind with `let`
first" [fn: build/coordinator/lanedumps/cut-m2a-lb-continuation.md:26
@worktree].

## 5.3 No consing on hot paths: finding the consing

### What goes wrong

A list costs sixteen bytes per element to build. Building a list of
1,000,000 naturals allocated 15,986,880 bytes on the laptop; the same
numbers written into the stobj array allocated 0 [example:
examples/performance/time-list-vs-stobj.lisp] [measured: `time-list-vs-stobj.cert.out` lines
792 and 797; laptop]. The scan over either allocated nothing, and the list
scan was not slower: 100 scans of 1,000,000 words took 0.23 s over the list
and 0.26 s over the stobj (an earlier certification of the same book printed
0.22 s and 0.25 s) [measured: `time-list-vs-stobj.cert.out` lines 793 and 798;
laptop]. The difference is the build and the access by position: 100 reads
of word 999,999 took 0.10 s by `nth` and 0.00 s (below the timer's
resolution) by the array accessor [measured: `time-list-vs-stobj.cert.out` lines 794 and
799; laptop]. So the cost of a list representation is what it allocates,
what it retains and what it makes linear, not the speed of a sequential
pass over it. Section 5.4 is the history of what that cost fn.

### The tools

**`time$`.** "Semantically, `(time$ x ...)` equals `x`. However, its
evaluation writes timing output to the trace output" [:doc time$]. It can be
called inside function bodies, which is how a test book measures one
sub-computation without the cost of building its inputs [:doc time$]. Its
options, quoted from the general form: `:real-mintime` (or `:mintime`),
`:run-mintime`, `:minalloc`, `:msg` and `:args` [:doc time$]. The `:msg`
directives include "`~sa` -- the amount of memory allocated, in bytes (in
supported Lisps)" and "`~st` -- the real time taken, in seconds" [:doc
time$]. The bare form prints the host's own report; on the laptop `(time$
(len (mklist 1000000 nil)))` printed `; 0.01 seconds realtime, 0.01 seconds
runtime ; (15,986,880 bytes allocated).` [measured: `(defun mklist (n acc) ...)`
(a tail-recursive list builder) then that `time$` form, laptop REPL]. A message
with `:mintime 0` always prints; the timing example uses that form for
every line [example: examples/performance/time-list-vs-stobj.lisp].

Two cautions, both from the manual. Thresholds are a filter: "no timing
information will be printed if the execution of `form` takes less than the
specified number of seconds" [:doc time$]. And at the top level, without
`:msg`, "an explicit call of `time$` in the top-level loop will show that
the form being timed is a call of the ACL2 evaluator function `ev-rec`"
[:doc time$].

**A test book as the record.** A `time$` inside an `assert-event` prints
while the book certifies, so the `.cert.out` is a dated record of the
numbers. It does not print when the book is included: "keyword
`:on-skip-proofs` can override the default behavior of ignoring assertions

### fn's hot-path checker: the idea and its limits

The rule fn enforced: "A function called once per request, arrival or
contact must not traverse a collection whose size does not depend on that
request" [fn: docs/proof-style.md:858-860 @3bbfc4dca]. The checker
(`tools/hot_path_check.py`) "seeds the accessors whose value grows with
retained state ... It follows each seeded value from every `host/` and
`host/native/` definition down the path that executes. Each traversal it
reaches is reported: `len`, `nthcdr`, `member`, `append`, `reverse`, a
recursion down the list, `dolist`/`loop`, or a list conversion" [fn:
docs/proof-style.md:861-867 @3bbfc4dca]. It classified each find as cold,
resumable, output-proportional, unexpected or uncalled [fn:
docs/proof-style.md:881-888 @3bbfc4dca]. Its own list of what it could not
see is the honest part: "It is path-insensitive ... It is
context-insensitive ... It does not expand macros. It treats `equal` as
constant time", and "The tool's silence is not a proof" [fn:
docs/proof-style.md:896-909 @3bbfc4dca].

The wound is what happened next. Commit `9d5a3f99b` on `origin/dev`
("M1-d ring 2: depth, hot-path, teeth, reach, theory and the resilience
checker leave") deleted `tools/hot_path_check.py` and its dimensions file,
and the Makefile lost the `hot_path` step [fn: commit 9d5a3f99b, an
ancestor of @3bbfc4dca]. Section 11 of `docs/proof-style.md` at the same sha still says
the checker "runs in `make check` (`--summary --strict`)" [fn:
docs/proof-style.md:861 @3bbfc4dca]. A rule whose checker has been deleted
is a comment; the document should say which. The shape that survives a
checker's deletion is an allocation bound stated in the logic, which fn's
`defteeth` provided for: "states cost bounds (`:visits`, `:allocation`) with
the state that attains them" [fn: docs/proof-style.md:358-360 @3bbfc4dca].

## 5.4 The representation lesson

fn's history with octet lists is the performance request its owner made most
often, and the record shows a failure of process more than of technique: the
technique was built and the old path was kept [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:42-48 @worktree].

The decision was made early and stated well. D27, written from ember's
"Using octet lists continues to be unacceptable at runtime" (2026-09-25):
"**The logical model stays octet lists; the executable path does not.**
Record bodies, frames, headers, the Message-ID index and the in-memory
history get concrete representations (stobj byte arrays, strings, arrays)
with a correspondence theorem to the list definition at every boundary the
host calls, guard-verified, and measured before and after on the same
image" [fn: build/coordinator/REPRESENTATION-HISTORY-20261028.md:17-18
@worktree]. ember asked for the same thing "six times in five weeks ... and
twice more as decisions (D27, D41)" [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:42 @worktree].

The concrete representations were built. The octet buffer, the payload
arena, the paged catalog, the linear-hashing Message-ID pages and the paged
history "all landed and are attached. What did not happen is the second half
of each landing: deleting the list path it was built to replace" [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:48 @worktree]. The
measure is the host's list conversion `fnn-octet-list`, `(coerce octets
'list)`, counted at the last `dev` commit before each date [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:48-59 @worktree]:

| date | `(fnn-octet-list` calls in host |
| --- | ---: |
| 2026-09-22 | 130 |
| 2026-09-25 (D27; the octet buffer and the arena land) | 179 |
| 2026-09-27 | 213 |
| 2026-10-01 (D41) | 238 |
| 2026-10-05 | 242 |
| 2026-10-09 (freeze) | 252 |
| 2026-10-14 | 263 |
| 2026-10-17 to `3bbfc4dca` | 263 |

"The count grew in every period after D27" [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:61 @worktree]. Traced
at `3bbfc4dca`, a POST from socket to log goes through "18 whole-article
representation changes, 16 under the owner mutex", among them a list of line
lists, a flat cons list, one bignum and back [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:89-108 @worktree]. The
read path is the counter-example: ARTICLE makes "3 whole-article copies,
all buffer to buffer, no octet list", so "the read path is what D27 asked
for, and the write path is not" [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:112-114 @worktree].

Why it happened, in the investigation's words: "The design law the waves
were written under (D27: 'a correspondence theorem to the list definition at
every boundary the host calls') made each new buffer path a **twin** of a
list path, proved equal to it. The list path stayed callable, and new host
code kept calling it" [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:136 @worktree]. The
tree's own count of the result was "494 loop twins and 285 representation
twins" (D62) [fn: build/coordinator/REPRESENTATION-HISTORY-20261028.md:34
@worktree]. The generator added to the problem: `def-representation`'s
`:generic t` emits "an ATTACHABLE generic over a LIST foundation (one field
holding the logical value, every :exec a total list operation ...)" beside
the columnar instance [fn: books/def-representation.lisp:42-49
@3bbfc4dca], so even a generated concrete representation came with a list
implementation that host code could select.

The lesson, as the investigation states it: settle what an article's bytes
are "as one value with one owner, from the socket read to the log write ...
with the octet list confined to `:logic` and never callable from `:exec`",
"then delete the list paths it replaces in the same landing" [fn:
build/coordinator/REPRESENTATION-HISTORY-20261028.md:183 @worktree]. In
ACL2 terms:

- the list is the `:logic` side of an `mbe`, or the abstraction function of
  an abstract stobj, and nothing else;
- the correspondence theorem is proved once, at the representation, not at
  every caller (D30's repair: "representation as a named abstraction or
  refinement theorem at each boundary rather than a twin of every helper")
  [fn: build/coordinator/REPRESENTATION-HISTORY-20261028.md:19 @worktree];
- a landing that adds a concrete path removes the list path in the same
  change, and a count of the list path's call sites is the measure (fn had
  one, `tools/list_codec_check.py`, whose baseline "last moved on 2026-10-02
  ... No lane has lowered it since") [fn:
  build/coordinator/REPRESENTATION-HISTORY-20261028.md:61 @worktree].

## 5.5 Batching and group commit as modelled state

### What goes wrong

A commit that pays one barrier (one `fdatasync`) per record is bounded by
the barrier's latency. A commit that batches but whose batching lives in the
host is an unverified scheduler deciding what is durable. fn's anatomy names
the second as its second sin: "The books decide what the owner does; the
host decides when, under which lock, on which thread" [fn:
build/coordinator/ANATOMY-20261009.md:27 @worktree].

### The mechanism, as fn modelled it

fn's storage specification states the batch as a machine with its own
rules. STO-033: "One batch of prepared commits is in flight at a time ...
and its members are ordered by their prepare. A member is acknowledged only
after the batch's barrier, and in order. The batch closes when the log
thread returns from the previous barrier or at the operator's live bounds
`log-batch-records` and `log-batch-octets` ... and never on a timer: at one
poster the batch is one entry and its latency one barrier. A failed barrier
makes every member in flight or waiting uncertain and fences the store;
recovery holds the committed records followed by a prefix of the batch, so
an acknowledged member is never lost and an unacknowledged one may appear"
[fn: specs/storage.md:443-455 @3bbfc4dca]. The format row, STO-028, puts the
batch in the log itself: "one self-checking chained entry per record or
batch, one barrier per batch of commits" [fn: specs/storage.md:1786-1791
@3bbfc4dca], and the store's summary line repeats it [fn:
docs/implementation.md:47 @3bbfc4dca]. STO-034's segment rotation is
scheduled around the batch, not across it: the switch to a new segment
happens "under the mutex with no batch in flight" [fn:
specs/storage.md:563-572 @3bbfc4dca].

The record log carries the batch in its format: "kind 2 is two or more
records, each after its length in four octets (PKT-749, lane log-2-pad: a
batch is one entry padded once, not one padded entry per record; -37.5
percent of the log for eight 2 KiB articles at the 4 KiB unit)" [fn:
books/store-log.lisp:9-13 @3bbfc4dca]. The commit route makes the batch the
unit of durability: "the ENTRY's durability is the batch's barrier
(fn-lgk-fence), and no reply, feed resolution or read leaves the owner
before it" [fn: books/owner-log-route.lisp:18-25 @3bbfc4dca]. And the
pipelined form overlaps the barrier with the next batch: "the next batch
prepares while the batch in flight's fdatasync runs ... Nothing is appended:
fn-lgk-append refuses while a batch is in flight, so the log's order is the
batches' order" [fn: books/owner-commit-pipeline.lisp:1-22 @3bbfc4dca].

Two remarks on the fn text. The header of `books/store-log.lisp` says both
"Nothing here is guard-verified: this is the prototype book" and, fifty
lines later, "The log's functions execute guard-verified, every walk by a
loop" [fn: books/store-log.lisp:52-53, 102 @3bbfc4dca]; a header that
contradicts itself is a header nobody rewrote whole. And STO-033 says "no
host line calls" the batch layer yet [fn: specs/storage.md:455-457
@3bbfc4dca], which is the cost of the host deciding: the model existed
before the program used it.

### The shape to copy

The batch is state; the barrier's completion is an event; the invariant is
about acknowledgement and durability. The deterministic-simulation example
is that machine cut to its skeleton (open batch, one in flight, a durable
log, the acknowledged list, a fence), with the invariant "every acknowledged
member is in the log, in order, and while not fenced nothing in the log is
unacknowledged" proved for the step and also checked after every step of
seeded runs [example: examples/performance/deterministic-simulation.lisp]:

```lisp
(defun gc-invp (s)
  (declare (xargs :guard (gc-statep s)))
  (and (prefixp (gc-acked s) (gc-durable s))
       (or (gc-fenced s) (equal (gc-acked s) (gc-durable s)))))

(defthm gc-step-preserves-invariant
  (implies (and (gc-statep s) (gc-invp s))
           (gc-invp (mv-nth 1 (gc-step ev s))))
  :hints (("Goal" :in-theory (disable prefixp-when-equal-lengths))))
```

The batch bound is a `defconst` (`*batch-max*`) in the state recognizer, and
a prepare to a full batch answers `:batch-full` and changes nothing [example:
examples/performance/deterministic-simulation.lisp]. TigerBeetle's version
of the same economics: "the cost of replication is paid only once per
batch", and "under light load, the batches automatically become smaller,
trading unnecessary throughput for better latency" [paper:
tigerbeetle2026-concepts-performance.md, "Batching, Batching, Batching"].

## 5.6 One executor loop

### What goes wrong

When the host owns threads and locks, the books cannot say anything about
them. fn's anatomy at the freeze counted "620 host functions (16.5K lines)
[that] branch on policy with no book deciding: lock order, cache hits,
cold-wait queues, the connection cap. owner.lisp has 163 threading and mutex
sites, io.lisp 65 ... the 52 lock keys and the failed phase-model lanes
follow from that" [fn: build/coordinator/ANATOMY-20261009.md:27 @worktree].
ember's question at the rethink was short: "huhm do you think one loop would
be burdensome?" [fn: build/coordinator/EMBER.md:297-301 @worktree].

### The mechanism

The runtime model fn drafted for the rewrite makes the loop the contract:
"The owner machine has exactly one executing thread. I/O workers execute
actions and return completions as events; they never drive the machine.
Synchronization exists around the event queue and root publication only.
Correctness is single-writer ownership plus explicit transfers, not 'a mutex
makes it sequential'" [fn: build/coordinator/RUNTIME-MODEL-DRAFT-20261009.md:10
@worktree]. Every effect is an identified action and the only input is its
completion: "An action is `(kind id incarnation op args)`, `op` an operation
number so two actions of one kind on one slot are never confused ... the
host delivers exactly one completion per submitted action
(A-HOST-COMPLETES). Submission order establishes nothing" [fn:
build/coordinator/RUNTIME-MODEL-DRAFT-20261009.md:9 @worktree].

`books/runtime-contract.lisp` is that layer, written once "over a
constrained instance machine (`fn-rtc-m-step`), so its theorems hold for
every machine that meets the constraint; an executable instance obtains them
by `:functional-instance`" [fn: books/runtime-contract.lisp:12-15
@3bbfc4dca]. What the layer owns, from its header [fn:
books/runtime-contract.lisp:17-111 @3bbfc4dca]:

- **Slots**, one per instance, "(incarnation status resource)"; "A slot is
  retired to :free only when its incarnation has no outstanding action, and
  an :accept reuses it under incarnation + 1."
- **The pool** of buffers, each in a named ownership state: `:free`,
  `(:workspace id inc)` ("mutable, one instance"), `(:leased id inc dir)`
  ("immutable to every instance") or `(:handed id inc to tinc)`; at an action
  boundary a buffer is a handle `(h g off len)`.
- **Uses**, the outstanding-action table, "one per submitted action until its
  completion arrives".
- **The borrowed view**: the machine "receives its own view of the pool,
  `fn-rtc-view`, which it cannot write and in which only its own workspaces'
  and its own :out leases' octets are present", so "no machine observes
  octets a worker may be writing" and none observes another instance's.
- **Leases**: the invariant "OutstandingUse(h,g) => BytesStable(h,g) and not
  Recyclable(h,g)" is a clause of the layer's invariant plus a two-state
  theorem.
- **A work budget**: "one step costs at most q + (fn-rtc-step-c config)",
  and "Work an instance cannot finish within q stays in its own state and
  resumes on the completion of a zero-delay :timer it submits; there is no
  other continuation mechanism."
- **The commit point**: ":commit is not an action kind. An instance's commit
  observer ... may turn true only on the delivery of a (:fsync (:done n))
  completion of the instance's own outstanding :fsync."

A completion that matches no outstanding use "changes nothing and emits
nothing (T6). The layer checks the host's discipline; it does not assume
it" [fn: books/runtime-contract.lisp:62-65 @3bbfc4dca]. Its own stated
limitation is worth copying as a form: "v1 limitation: one outstanding
action per (kind id inc) ... Revisit when a measured served path needs it"
[fn: books/runtime-contract.lisp:82-87 @3bbfc4dca].

TigerBeetle reaches the same structure from the performance side: "TigerBeetle
is single-threaded ... keeping the system single threaded greatly simplifies
the programming model and makes testing much more efficient" [paper:
tigerbeetle2026-architecture.md, "Single Thread"], and "Each TigerBeetle
'future' is represented by an explicit struct which is statically allocated
as a field of a component that owns the structure. There's always a natural
limit of how many concurrent tasks can be in flight!" [paper:
tigerbeetle2026-architecture.md, "Static Memory Allocation"]. fn's slots and
uses are those structs.

### The shape to copy

One step function over the state and one event; the event list is the
input; the host's only job is to perform actions and deliver completions.
The deterministic-simulation example is a step function of that kind
[example: examples/performance/deterministic-simulation.lisp]; fn's
contract book is the full version, with the constrained machine as the
parameter [fn: books/runtime-contract.lisp:12-15 @3bbfc4dca].

## 5.7 TigerStyle in ACL2

TigerBeetle's coding rules (`docs/TIGER_STYLE.md`, fetched for this chapter
on 2026-10-28 and byte-identical to the copy in the paper bin) are written
for Zig. Most of them have an ACL2 form, a few have a stronger one, and two
do not translate directly. Each rule is quoted, then translated.

**"Assertions detect programmer errors ... The only correct way to handle
corrupt code is to crash. Assertions downgrade catastrophic correctness bugs
into liveness bugs"** [paper: tigerbeetle2026-tiger-style.md, "Safety"].
ACL2 has four assertion forms, and they are different things:

- a guard is an assertion that is *proved* at every call site inside
  verified code, and checked at run time only where a call enters verified
  code from outside: "This ability to dive into raw Common Lisp hinges on the
  proof that the guards you attach to your own functions are sufficient"
  [:doc guards-and-evaluation];
- `mbt` is a test the logic needs and the proof erases ("macroexpands to
  `t`") [:doc mbt];
- `assert$` "checks the assertion at runtime" and, in guard-verified code,
  creates "a proof obligation ... that the occurrence of `test` is never
  `nil`" [:doc assert$]; `assert*` creates the obligation without the
  runtime check [:doc assert$];
- `assert-event` is a check on a value when the book is processed, skipped
  by default during `include-book` [:doc assert-event].

TigerBeetle "keeps these assertions on, even in production. The logic is
that it is far better to stop operating than to continue operating in an
incorrect state" [paper: tigerbeetle2026-internals-vopr.md, lines 50-54].
The ACL2 version keeps the property and drops the run-time cost where the
property is proved: a verified guard is an assertion that cannot fail on a
call made from verified code. What remains to check at run time is the
boundary, where input is not produced by verified code; that is one entry
check that refuses by name (`admit-batch` in the limits example) and a guard
on everything behind it [example: examples/performance/limits-as-guards.lisp].

**"Put a limit on everything ... all loops and all queues must have a fixed
upper bound to prevent infinite loops or tail latency spikes"** [paper:
tigerbeetle2026-tiger-style.md, "Safety"]. In ACL2 a loop terminates by its
measure, which the definition must prove; the *bound* is a separate claim:
a `defconst`, used in the guard and in the theorems. The limits example
keeps its limits in one table read by a macro, so the admitted term is the
number itself, and proves that the batch's answer never exceeds its ceiling
[example: examples/performance/limits-as-guards.lisp]:

```lisp
(defconst *line-octets-max* 512)
(defconst *batch-records-max* 64)
(defconst *batch-octets-max* (* *batch-records-max* *line-octets-max*))

(defmacro limit (name)
  (let ((pair (assoc-eq name *limits*)))
    (if (consp pair)
        (cdr pair)
      (er hard 'limit "No limit named ~x0 in *limits*." name))))

(defthm admit-batch-answer-is-within-the-ceiling
  (<= (mv-nth 1 (admit-batch l)) (limit :batch-octets))
  :rule-classes :linear
  :hints (("Goal" :use ((:instance batch-octets-spec-bound
                                   (max (limit :line-octets)))))))
```

The macro is fn's trick from its protocol table: "`fn-proto-text` is a
MACRO, so the term a book admits is the literal itself and no proof or
execution sees a lookup" [fn: books/protocol-table.lisp:300-302 @3bbfc4dca].

**"Assert the relationships of compile-time constants as a sanity check"**
[paper: tigerbeetle2026-tiger-style.md, "Safety"]. In ACL2 that is an
`assert-event` over `defconst`s, checked when the book certifies:

```lisp
(assert-event (equal *batch-octets-max* (* *batch-records-max* *line-octets-max*)))
(assert-event (< *batch-octets-max* (expt 2 60)))
```

[example: examples/performance/limits-as-guards.lisp]. The bounded-table
example uses it to tie a literal that a type-spec must spell
(`(integer 0 64)`) back to the constant it repeats [example:
examples/performance/bounded-table.lisp].

**"Use explicitly-sized types like `u32` for everything"** [paper:
tigerbeetle2026-tiger-style.md, "Safety"]. In ACL2: `(unsigned-byte 32)`
as a `type` declaration and in `the`, which are guard obligations and
useful to the compiler only once guards are verified [:doc the]. The width
that matters on SBCL is the fixnum: fn chose `(unsigned-byte 61)` page words
so that the accessor returns them unboxed [fn:
books/msgid-linear-exec.lisp:26-31 @3bbfc4dca].

**"All memory must be statically allocated at startup. No memory may be
dynamically allocated (or freed and reallocated) after initialization"**
[paper: tigerbeetle2026-tiger-style.md, "Safety"]. TigerBeetle is precise
about what that means: "for every 'object type' in the system it computes
the worst-case upper bound for the number of objects needed, based on CLI
arguments. Then TigerBeetle allocates exactly that number of objects and
enters the main event loop" [paper: tigerbeetle2026-architecture.md,
"Static Memory Allocation"]. In ACL2 the stobjs are those objects: arrays of
fixed length, created once, never resized, every insert bounded and refused
when full (5.2). ACL2 cannot promise that nothing else allocates: a `cons`
on the `:exec` side does, and so does a `with-local-stobj` per call (5.2).
The claim to make is measured, per operation, in a test book: "0 bytes" over
the operation, with the operation named [example:
examples/performance/time-list-vs-stobj.lisp]. TigerBeetle's reason applies
unchanged: "static allocation is a forcing function to ensure that
everything has a limit" [paper: tigerbeetle2026-architecture.md, "Static
Memory Allocation"].

**"The golden rule of assertions is to assert the positive space that you do
expect AND to assert the negative space that you do not expect"** [paper:
tigerbeetle2026-tiger-style.md, "Safety"]. That is a keystone's teeth: a
witness where the conclusion fires and a value that violates the conclusion
when a hypothesis is removed (chapter 6, "Teeth").

**"Assertions are a safety net, not a substitute for human understanding.
With simulation testing, there is the temptation to trust the fuzzer. But a
fuzzer can prove only the presence of bugs, not their absence"** [paper:
tigerbeetle2026-tiger-style.md, "Safety"]. TigerBeetle's simulator: "all
non-deterministic parts of the system are stubbed out. This includes the
clock, network, and disk operations. The VOPR uses a random seed to tune
parameters for injecting different types of faults", and "the seed and Git
commit hash can be used to replay back the exact simulation and bug" [paper:
tigerbeetle2026-internals-vopr.md, lines 29-40]. In ACL2 the system under
simulation is already a step function over an event list, so a
deterministic simulation is a test book: a seeded generator, a bounded
event list, and a loop that checks the invariant after every step and
answers the first violation [example:
examples/performance/deterministic-simulation.lisp]:

```lisp
(defun run-check (events s i mutantp)
  (declare (xargs :guard (and (gc-statep s) (natp i))
                  :measure (len events)))
  (cond ((atom events) :ok)
        (t (mv-let (word s2)
             (if mutantp (gc-step-mutant (car events) s) (gc-step (car events) s))
             (declare (ignore word))
             (if (and (gc-statep s2) (gc-invp s2))
                 (run-check (cdr events) s2 (+ 1 i) mutantp)
               (list :violated-at i (car events)))))))

(assert-event (eq (all-seeds-ok 50 2000 nil) :ok))
(assert-event (equal (all-seeds-ok 50 2000 t)
                     '(:seed 50 (:violated-at 28 (:seal)))))
```

The second assertion is the part fuzzers usually lack: a mutant step that
acknowledges at the seal, before any barrier, must be caught, and because
the run is deterministic its report is a constant the book can state [example:
examples/performance/deterministic-simulation.lisp]. fn's lane that built
differential tests over its catalog stated the rule that makes such a
mutant worth anything: "a teeth run that mutates ONE side at a reachable
version and must be caught. A teeth mutation visible only at an unreachable
version (count+1) proves nothing. Fixed-seed LCG generators, 300 seeds x 40
steps run in seconds in the REPL" [fn:
build/coordinator/lanedumps/cut-m2a-lb-continuation.md:17 @worktree]. In
ACL2 the simulation and the proof sit side by side: the example also proves
`gc-step-preserves-invariant`, and the simulation's job in a real node is
the part the proof does not cover, the host [example:
examples/performance/deterministic-simulation.lisp].

**"Don't do things directly in reaction to external events. Instead, your
program should run at its own pace ... you get to batch, instead of context
switching on every event"** [paper: tigerbeetle2026-tiger-style.md,
"Safety"]. That is the one executor over completions (5.6) and the batch
that closes when the barrier returns, never on a timer (5.5).

**Two rules that do not translate directly.** "Do not use recursion"
[paper: tigerbeetle2026-tiger-style.md, "Safety"]: ACL2 definitions are
recursions; the translation is that every recursion has a measure the
definition proves, a bound in its guard, and an accumulator form for the
`:exec` side, which the host Lisp may run as a loop ("if your Common Lisp or
its compiler does such optimizations as tail-recursion removal") [:doc
guards-and-evaluation], while an unverified one runs in `*1*` as a
recursion [fn: books/store-log.lisp:102-108 @3bbfc4dca]. And the "hard
limit of 70 lines per function" [paper: tigerbeetle2026-tiger-style.md,
"Safety"] has no measured ACL2 counterpart in the sources this guide read;
fn's nearest rule is about books, not functions: "Split a book over 800
lines at its seam" [fn: docs/proof-style.md:411 @3bbfc4dca].

## 5.8 Code generation: ATC, APT, and what fn did instead

The first thing the ATC paper says about code generation from ACL2 is that
it is often unnecessary: "ACL2's tight integration with the underlying Lisp
platform may obviate the need for code generation, because executable ACL2
code can run efficiently as Lisp" [paper:
coglio2022-acl2-atc-proof-generating-c-code-generator.txt, section 1]. The
reasons to generate anyway are a target that is not Lisp (C for embedded
code, a component of another system) and a shipped artifact much smaller
than an ACL2 image.

Neither ATC nor APT is certified on the laptop, and their closures take
longer than an example may, so this section cites their own documentation
and tests by path; the examples are theirs (`sources.md`, "Toolchain").

### ATC: C from a shallow embedding of C

ATC "recognizes ACL2 representations of C constructs, according to a
shallow embedding of C in ACL2, and translates those representations to the
represented C constructs. The code generator also generates ACL2 theorems
asserting the correctness of the C code with respect to the ACL2 code"
[paper: coglio2022-acl2-atc-proof-generating-c-code-generator.txt,
abstract]. The paper names the direction: "code generation by inverse
shallow embedding: the embedding is a (not necessarily reified) translation
from the programming language to the prover's language, and the code
generator is the (reified) inverse translation" [paper:
coglio2022-acl2-atc-proof-generating-c-code-generator.txt, section 1]. So
the ACL2 you hand ATC is "essentially 'C written in ACL2'" [books:
kestrel/c/atc/tutorial.lisp, page `approach`].

What a target function must be, quoting the reference manual:

- "Each target function `fn` must be in logic mode and guard-verified"
  [books: kestrel/c/atc/doc.lisp:328].
- "If `fn` is recursive, it must be singly (not mutually) recursive, its
  well-founded relation must be `o<`, and its measure must yield a natural
  number"; recursive targets "represent loops in the C functions" [books:
  kestrel/c/atc/doc.lisp:316-320, 375-380].
- "The guard of each `fn` must include, for every formal parameter `x`,
  exactly one conjunct of one of the following forms ... which determines
  the C type of the corresponding parameter": `(ucharp x)` for `unsigned
  char`, `(uintp x)` for `unsigned int`, and so on through `(ullongp x)` and
  the pointer forms `(star (ucharp x))` [books:
  kestrel/c/atc/doc.lisp:383-420].

The last rule corrects a natural assumption. A function with
`(unsigned-byte 32)` guards is not what ATC translates; ATC's integer
values are the C library's own types, and the operations are the C
operations over them. Kestrel's checksum test is the clearest example: the
guard says `(c::uintp |current|)` and `(c::ucharp |hibyte|)`, and the body
is `(c::bitand-uint-uint (c::add-uint-uint |current| (c::add-uint-uint
(c::shl-uint-sint (c::uint-from-uchar |hibyte|) (c::sint-dec-const 8))
(c::uint-from-uchar |lobyte|))) (c::uint-dec-const 65535))`, then `(c::atc
|legacy| |checksum| :file-name "checksum" :header t)` [books:
kestrel/c/atc/tests/checksum.lisp:93-116]. A loop is a recursive function
over C values with its measure in C terms, `:measure
(c::integer-from-uint |n|)` [books: kestrel/c/atc/tests/loops.lisp:24-45].
Getting from ordinary ACL2 (with `(unsigned-byte 32)` guards) to that form
is the job of APT's transformations: "One uses APT transformations to refine
ACL2 specifications and code to the subset recognized by ATC, which ATC
translates to C" [books: kestrel/c/atc/tutorial.lisp, page `approach`].

What ATC generates besides the files: `(defconst *program* ...)`, the
abstract syntax; `(defthm *program*-well-formed ...)`, that the files are
"statically well-formed, i.e. it compiles according to [C17]"; and for each
target `(defthm *program*-fn-correct ...)`, "that, under the guard of `fn`,
executing the C dynamic semantics on the C function generated from `fn`
yields the same result as the function `fn`" [books:
kestrel/c/atc/doc.lisp:1536-1567]. The fine print is an assumption about
the caller: "The formal model of C that the proofs rely on assumes that
objects do not overlap. Thus, the guarantees provided by the generated
theorems about the C code hold only if pointers to distinct, non-overlapping
objects are passed to the generated C functions" [books:
kestrel/c/atc/doc.lisp:1564-1572]. And the guard requirement is what rules
out undefined behaviour: it "implies that the generated C operations never
exhibit undefined behavior, provided that they are called with values whose
ACL2 counterparts satisfy the guard of the function" [books:
kestrel/c/atc/doc.lisp:1588-1593].

The `.c` files in `kestrel/c/atc/tests/` are the "handwritten C code to test
the generated code" [books: kestrel/c/atc/doc.lisp:1615-1617]
(`checksum-test.c` calls `checksum(current, hibyte, lobyte)` and prints the
result); the generated `checksum.c` and `checksum.h` appear only when
`checksum.lisp` is certified, and `compile.sh` builds each pair with `gcc`
[books: kestrel/c/atc/tests/checksum-test.c] [books:
kestrel/c/atc/tests/compile.sh].

### APT: transformations that carry their theorems

APT is "a library of tools to transform programs and program specifications
with automated support"; its tools "generate corresponding transformed
artifacts along with theorems asserting the relationship (e.g. equivalence)
between old and new artifacts", and "modify the ACL2 state only by
submitting sound and conservative events; they cannot introduce unsoundness
or inconsistency on their own" [books: kestrel/apt/doc.lisp:68-85]. The ones
that matter for a representation change, each with its own documentation and
test book:

| transformation | what it does (its `:short`) | files |
| --- | --- | --- |
| `isodata` | "change function arguments and results into isomorphic representations" | `isodata-doc.lisp`, `isodata-tests.lisp` |
| `expdata` | "change function arguments and results into expanded representations" (a surjection from new to old, not an isomorphism) | `expdata-doc.lisp`, `expdata-tests.lisp` |
| `parteval` | "specialize a function by setting one or more parameters to specified constant values" | `parteval-doc.lisp`, `parteval-tests.lisp` |
| `finite-difference` | "finite-differencing, aka incrementalization" | `finite-difference.lisp` (its doc is in the source), `finite-difference-tests.lisp` |
| `casesplit` | "rephrase a function definition by cases" | `casesplit-doc.lisp`, `casesplit-tests.lisp` |
| `lift-iso` | "Lift an isomorphism to an isomorphism on a structure containing the original isoporphism predicate" [sic] | `lift-iso-doc.lisp`, `lift-iso-tests.lisp` |
| `tailrec` | "turn a recursive function that is not tail-recursive into an equivalent tail-recursive function" | `tailrec-doc.lisp`, `tailrec-tests.lisp` |

[books: kestrel/apt/isodata-doc.lisp:33-35] [books:
kestrel/apt/expdata-doc.lisp:37-61] [books: kestrel/apt/parteval-doc.lisp:32-34]
[books: kestrel/apt/finite-difference.lisp:35-38] [books:
kestrel/apt/casesplit-doc.lisp:32-33] [books: kestrel/apt/lift-iso-doc.lisp:25]
[books: kestrel/apt/tailrec-doc.lisp:32-34]. `isodata` is the one that does
in one event what fn did by hand in twins: it "changes the representation of
one or more of a function's arguments and results into an isomorphic
representation", which is "useful to carry out certain data type refinements
(when synthesizing programs), or to raise the level of abstraction of certain
types (when analyzing programs)" [books: kestrel/apt/isodata-doc.lisp:47-55].
The paper on it is in the bin [paper:
coglio2020-acl2-apt-isomorphic-data-type-transformations.txt].

The route to a tiny shipped core, then, is a derivation: a specification in
ordinary ACL2, a chain of APT transformations each with its equivalence
theorem, ending in ATC's subset, then C with its correctness theorem. "With
the ACL2-to-ACL2 proofs in an APT derivation, the ACL2-to-C proof generated
by ATC provides an end-to-end correctness proof of the synthesized C code"
[paper: coglio2022-acl2-atc-proof-generating-c-code-generator.txt, section
1]. Its limit is the subset: "integer types, operations and conversions on
them, integer arrays with read and (destructive) write access, local
variable declarations and assignments, loops of certain forms, conditional
expressions and statements, and functions that may affect arrays" [paper:
coglio2022-acl2-atc-proof-generating-c-code-generator.txt, section 1].

### What fn did instead: extraction to bare SBCL

fn shipped Lisp, and the question was which Lisp. ember, at the rethink:
"do we really need to be using ACL2's runtime if we have an extractor and
the 'official' version has extremely expensive per-thread overhead...??"
[fn: build/coordinator/EMBER.md:297-299 @worktree], and two days earlier, "I
think we should just have bare-SBCL if there is maintenance burden regarding
the two extractors" [fn: build/coordinator/EMBER.md:222-227 @worktree].

The extractor that survived exports the ACL2 world's translated definitions
as one file of units and loads them into bare SBCL with a small runtime: a
lane's record of the export reads "1957 roots -> 25376 units, 26 runtime
refs, 0 gaps; bare SBCL `load` of defs.lisp: 0 undefined fns, 0 WARNINGs",
with ACL2's own system functions "derived from ... acl2-8.7 sources (228
defuns+defstruct+defconst, file sha+line)" [fn:
build/coordinator/lanedumps/extract-forms.md:11-12 @3bbfc4dca]. The same
record lists the CHICKEN Scheme translator and its tests for deletion [fn:
build/coordinator/lanedumps/extract-forms.md:28-33 @3bbfc4dca]. What it
bought, in image size: at the freeze, "fn-host.core 244 MB,
fn-host-developer.core 660 MB, four image kinds plus fn-core (84 MB bare
SBCL)" [fn: build/coordinator/ANATOMY-20261009.md:67 @worktree], and the
two-week audit later records "the fn-core image (81.0 -> 74.3 MB,
extraction)" as one of the few things that shrank [fn:
build/coordinator/AUDIT-TWO-WEEKS-20261013.md:71 @worktree].

The contrast with ATC is the evidence. An extracted Lisp image runs the same
definitions ACL2 certified, so the proof applies to the code as far as the
extractor is faithful, and the extractor's faithfulness is a test-and-review
argument (fn kept a gate comparing fn-core against the ACL2 image [fn:
build/coordinator/lanedumps/extract-forms.md:34-36 @3bbfc4dca]). ATC's
output comes with `*program*-fn-correct`, a theorem in the logic, at the
price of the C subset.

## 5.9 What a metaprogramming layer buys and costs

### What it bought fn

fn's proof-style document opens with the table of conventions that "are now
machinery, and the machinery is the convention": `fn-defrecord` replaces
"eleven to forty-one hand-written events per record", `fn-deftransition`
replaces "a floating `(local (in-theory (disable ...)))` and hand-wired
branch lemmas" [fn: docs/proof-style.md:10-17 @3bbfc4dca]; one record
migration "removed 293 lines" [fn: docs/proof-style.md:43-44 @3bbfc4dca].
`def-loop` replaced a pattern that, "Written by hand ... is twenty-six lines,
one induction under `minimal-theory` and two guard proofs per loop, 850
inductions tree-wide, and every one of them the same induction"; the
generator proves "each SHAPE's bridge ... ONCE, over constrained functions
that have no axioms", and every instance gets its bridge "by
`:functional-instance` of that one theorem", whose obligation "one unfold of
each discharges in `minimal-theory`: no instance induction, no instance
hint" [fn: books/def-loop.lisp:5-21 @3bbfc4dca]. The protocol table replaced
"Five hand-kept copies of one table": "the dispatcher's arms, the RFC
citations ..., the accepted/refused/uncertain reading of each reply, the
fuzzer's grammar ... and the FAQ's command list" [fn:
books/protocol-table.lisp:4-9 @3bbfc4dca]. `definterface` replaced "four
hand lists in three tools" with one form "checked against the WORLD when it
is admitted" [fn: books/definterface.lisp:3-11 @3bbfc4dca]. `defteeth` binds
a keystone's teeth "to the theorem as the world stores it (the claim is
translated and compared)" [fn: docs/proof-style.md:352-355 @3bbfc4dca].

ember's framing of why: "relying on as much linguistic metaprogramming as we
need to not drive ourselves crazy, while also having a broad and wide base of
assurance built within acl2" [fn: build/coordinator/EMBER.md:293-295
@worktree], and "I think we probably should be adapting the generators ro
something right?? because without simplifying these things we'll never
actually finish the project" [fn: build/coordinator/EMBER.md:222-226
@worktree].

### What it cost fn

- **A static reader cannot see through a macro.** "Editing `fn-defrecord`
  means editing two files. `tools/ledger.py` mirrors the expansion
  (`defrecord_expansion`), because a static reader cannot see through a
  macro: without the mirror a migrated book loses forty names from the
  ledger's `definitions`" [fn: docs/proof-style.md:142-146 @3bbfc4dca]. The
  suspect detector "ignores `make-event`, which it cannot read statically"
  [fn: docs/proofs.md:226 @3bbfc4dca], and the hot-path checker "does not
  expand macros" [fn: docs/proof-style.md:902 @3bbfc4dca]. Every generator
  that a Python tool must understand is two implementations.
- **A generator high in the include graph recertifies everything.** "a change
  to `books/defrecord.lisp` --- a comment included --- invalidates its
  certificate and every certificate above it, so batch such changes" [fn:
  docs/proof-style.md:147-149 @3bbfc4dca]; in the generated table of
  dependents, `books/defrecord.lisp` has 1192 of 1370 [fn:
  docs/proof-style.md:459-462 @3bbfc4dca]. (The same document says a
  comment edit "recertifies nothing" because the hash is of forms, not bytes
  [fn: docs/proof-style.md:445-449 @3bbfc4dca]; the two sentences disagree.
  Measured: with `ACL2_BOOK_HASH_ALISTP=NIL`, a book certified, then edited
  in a comment only, included with no warning; the same book edited in a
  `defun` body was refused with `ACL2 Warning [Uncertified] ... lists the
  book-hash of that book as 138601362. But its book-hash is ...`. The hash is
  of the forms read, and the comment-edit sentence of `defrecord`'s header is
  wrong [measured: a two-event book `hx.lisp` certified with `cert.pl`, then
  `(include-book "hx")` after each edit, laptop ACL2 8.7 / SBCL 2.6.8,
  2026-10-28]. `cert.pl` still rebuilds on a changed file date, which is a
  different check.)
- **Options accrete.** `def-loop`'s header, after its five shapes, documents
  `:keep-order`, `:base` for two shapes, `:loop-guard`, `:acc-fix`,
  `:stobjs`, `:loop-guard-hints`, `:rev` and `:thread`, and a list of loops
  it still does not generate [fn: books/def-loop.lisp:69-128 @3bbfc4dca].
- **A generator does not delete what it replaces.** The twins counted by D62
  ("494 loop twins and 285 representation twins") were the backlog the
  generators were adopted to drain [fn:
  build/coordinator/REPRESENTATION-HISTORY-20261028.md:34 @worktree]; 5.4
  shows the representation half staying.

fn's anatomy puts both halves in one place. Sin 1, "Conceptual
multiplication in the definitions. Every storage concept is a ladder of
rungs, each reified as books with their own invariants, cursors, census and
refinement", is what generators were meant to collapse; sin 3, "The
apparatus outgrew the organism", is what the mirrors and checkers around them
became: "The checkers are a third again the size of the host they check"
[fn: build/coordinator/ANATOMY-20261009.md:26-28 @worktree]. The rule fn
wrote for the rewrite is the one to start from: "`def-pages`, `def-wire` and
`def-machine` are generalized from the first two working instances each, not
written as prerequisites" [fn:
build/coordinator/RUNTIME-MODEL-DRAFT-20261009.md:39 @worktree].

### What makes a generator cheap to read

`def-loop` already does the thing that removes the mirror: it records "a row
in the world table `fn-generated` naming what was generated, so a tool reads
the world rather than a mirror of this macro" [fn: books/def-loop.lisp:60-64
@3bbfc4dca], and `def-representation` records every instance in the same
table [fn: books/def-representation.lisp:75-78 @3bbfc4dca]. A static tool
that reads the world (from a certified image) needs no copy of any macro;
`definterface`'s check against "the WORLD when it is admitted" is the same
idea at admission time [fn: books/definterface.lisp:10-11 @3bbfc4dca].

### A sketch: three DSLs as the shape of a rebuilt fn

This is a design sketch, grounded in what fn's generators did, not a
description of anything that exists.

1. **A record and column DSL.** `def-representation` is the start: one
   declaration `(def-representation NAME (FIELD KIND) ...)` with KIND among
   `:u8 :u32 :u64 :bool :octets`, `(:nat B)` or `(:enum OBJ ...)`, which
   generates "the foundation of typed columns and one octet pool, the
   executables, the bridges by functional instance and by unfolding, the
   obligations obtained from ACL2 itself by `defabsstobj-missing-events` and
   closed by one uniform hint, the `defabsstobj`, the `-is-` meaning of each
   export" [fn: books/def-representation.lisp:6-18 @3bbfc4dca]. What the
   rebuild needs from it is one thing it did not do: no list foundation that
   `:exec` can select (5.4).
2. **A machine DSL.** The runtime contract written once over a constrained
   machine, every instance obtaining the layer's theorems by functional
   instance [fn: books/runtime-contract.lisp:12-15 @3bbfc4dca], with
   `def-carried` generating the carrying statements per transition and
   refusing unless "the vacuity probes fail" [fn: docs/proof-style.md:306-320
   @3bbfc4dca]. A declaration names the state, the events, the actions and
   the invariant; the generator emits the step's shape, the carry theorems
   and their teeth.
3. **A command-grammar DSL.** The protocol table is one: one row per
   command, its replies classed `:accepted`, `:refused` or `:uncertain`, the
   dispatcher's text generated from the `:arms` column, reply text read
   through a macro, the fuzzer's grammar emitted from the same rows by a
   non-evaluating reader [fn: books/protocol-table.lisp:13-80, 395-415
   @3bbfc4dca], and a theorem that "every reply code fn-nntp-command-pinned
   emits for a command is in that command's row" [fn:
   books/protocol-table.lisp:9-11 @3bbfc4dca].

Each of the three would record its instances in the world, so tools read
the world, and each would land with the code it replaces deleted.
